Static reducer trace only; I am not making any staging/production mutation or candidate-quality assertion.

The reducer **does not satisfy all MUSTs** in the ship contract, especially the correction, alternatives, pending, and strict confirmation boundaries in `.apr/specs/oriental-email-grounding-closure.md:5-25`.

## Blocking traces

1. **Strict readback confirmation can confirm a stale email from a contradictory user turn.**
   Scenario: email is pending after strict speech capture, assistant reads back `old@example.com`, user says: “Yes, actually use new@example.com instead.” If the model calls `confirm_email` with evidence `"yes"`, the reducer accepts it. The invalidator ignores pending verifications (`lib/voice/realtime-events.ts:676-679`), `confirmCapturedEmail` only checks explicit evidence, prior readback, and that the latest transcript contains the evidence substring (`lib/voice/realtime-events.ts:1538-1567`), and `isExplicitEmailConfirmation` accepts broad `"yes..."` prefixes without rejecting “actually/use/instead/new address” corrections (`lib/voice/realtime-events.ts:1593-1604`). It then stamps the verification sequence **after** that contradictory turn (`lib/voice/realtime-events.ts:438-443`), so future freshness checks see no newer correction (`lib/voice/realtime-events.ts:680-683`). A following `route_to_team` can submit because `isVoiceEmailConfirmed` passes and routing only blocks missing/invalid/unconfirmed fields (`lib/voice/realtime-events.ts:173-181`, `lib/voice/realtime-events.ts:505-536`).

2. **Alternatives not containing the current email leave a stale confirmed email routeable.**
   Scenario: current verified email is `old@example.com`; user later says, “Either new@example.com or alt@example.com works for my email.” The literal resolver detects alternatives, but if the current email is not one of them it returns `"none"` rather than `"different"`/`"ambiguous"` (`lib/voice/realtime-events.ts:1253-1278`). The spoken path has the same fail-open shape for unselected alternatives (`lib/voice/realtime-events.ts:730-737`). Since `emailCorrectionInvalidates` only invalidates on `"different"` or `"ambiguous"` (`lib/voice/realtime-events.ts:694-700`), the stale current verification survives and can route. That violates the stale-draft/unrouteable and alternatives coverage requirements (`.apr/specs/oriental-email-grounding-closure.md:18-19`, `.apr/specs/oriental-email-grounding-closure.md:29-31`).

3. **Pending relaxation can still re-confirm a stale duplicate after a completed bare replacement in aged-out history.**
   Duplicate email calls do cross grounding rather than early-returning (`lib/voice/realtime-events.ts:957-966`), but email grounding only searches the last six user turns (`lib/voice/realtime-events.ts:1086`). If a completed bare replacement contradicts the stale email while the original matching turn has aged out, `latestTurnSupersedes` can be true but miss the narrower rejection predicates, then `transcriptionPending` returns medium-confidence success anyway (`lib/voice/realtime-events.ts:1101-1111`). In adaptive mode that becomes confirmed speech verification (`lib/voice/realtime-events.ts:934-937`). This violates the rule that pending relaxation is allowed only when no completed turn contradicts the proposed address (`.apr/specs/oriental-email-grounding-closure.md:10-11`).

4. **Secondary billing/invoice “contact address” can invalidate a valid selected contact address.**
   The code has a secondary-address guard for billing/invoice/reference/support contexts (`lib/voice/realtime-events.ts:749-753`), but the guard is bypassed by broad “contact address” primary/selection cues (`lib/voice/realtime-events.ts:755-759`, `lib/voice/realtime-events.ts:1207-1211`). A turn like “For invoices, the billing contact address is bills@example.com” can be treated as a selected replacement because literal disposition marks “contact address is …” as selected (`lib/voice/realtime-events.ts:1297-1304`). That violates the requirement that a selected current contact address remain valid when a later address is clearly secondary, such as billing or invoices (`.apr/specs/oriental-email-grounding-closure.md:14-17`).

## Non-blocking / partially satisfied traces

- Recognized ordered literal and spoken forms such as “use new instead of old” are mostly handled: literal selected/rejected disposition is tracked (`lib/voice/realtime-events.ts:1260-1275`, `lib/voice/realtime-events.ts:1282-1306`), and spoken token-window selection/rejection exists (`lib/voice/realtime-events.ts:1213-1244`, `lib/voice/realtime-events.ts:1308-1338`).
- Exact duplicate call IDs are suppressed (`lib/voice/realtime-events.ts:310-319`), and new-call duplicate email captures are re-grounded (`lib/voice/realtime-events.ts:965-971`), but the pending/alternatives gaps above can still turn stale evidence back into success.
- Pending transcription identity is partly modeled with pending item IDs, response binding, and item-ID reconciliation (`lib/voice/realtime-events.ts:206-227`, `lib/voice/realtime-events.ts:254-262`, `lib/voice/realtime-events.ts:861-866`, `lib/voice/realtime-events.ts:633-636`), but the pending relaxation fail-open above prevents full contract satisfaction.
- Typed/prefill authority is partially protected: typed tentative capture records ignored pending transcript IDs (`lib/voice/realtime-events.ts:585-614`), ignored completions avoid reconciliation (`lib/voice/realtime-events.ts:230-242`), and confirmed typed/prefill verification is not overwritten by ordinary speech reconciliation (`lib/voice/realtime-events.ts:625-630`). However, the exported `confirmedEmailVerification` helper carries only the verification object, not chronology or ignored transcript IDs (`lib/voice/realtime-events.ts:165-171`), so the reducer contract is not self-contained unless every caller supplies the sequencing fields correctly.
